> 版本：v2.2 · 2026-10-21（变更：Java 端实现纯函数场、已加载区块查询、`/disaster ison` 与 10 s 运动步长）

## 0. 一句话

把"天灾中心"写成**静态锚点 + 有界巢域 + 低差异航点样条**的纯函数时空场：给定（世界种子、游戏刻、坐标）即可 O(1) 判定某处此刻有没有中心、位置在哪、是否被点亮、以及（设计上）是否有天灾正在生效——不需要逐刻模拟、不保存任何中心状态。

## 2. 核心模型：纯函数时空场

### 2.1 为什么必须"有界"

- R3 要求中心位置写成时间的纯函数 P(c,t)，不能依赖历史状态；
- R1 要求中心无限，所以"判定 p 处有没有中心"只能由 p 附近的**静态局部信息**产生候选；
- 若每个中心都能各自无界漂移，世界运行越久，任意远处的中心都可能出现在 p，候选集合半径随 t 无界增长 ⇒ O(1) 查询不成立。

> **有界性命题**：在"无限时间 + 无限中心 + O(1) 点查询"下，每个中心相对静态锚点的位移必须有与时间无关的上界 R，且 R = O(L)（L 为锚点格距）。唯一例外是"全体中心共享同一个随时间变化的坐标变换"（整体平移/旋转），因为查询只需一次逆变换。

所以"巢域"不是美术妥协，而是可计算性要求；这也决定了"大范围游走"只能靠**分层/放大尺度**，不能靠单个中心无界漂移。

### 2.2 三层结构

- **L1 锚点层**：世界切成 L×L 的格，每格恰好 1 个锚点，位置哈希抖动。
- **L2 巢域层**：每个中心永远位于其锚点周围半径 R 的圆盘内。
- **L3 轨迹层**：在巢域内取一串低差异目标点，用 C¹ 的 Catmull–Rom 样条连成轨迹；位置是段号与段内相位的函数。

## 3. 算法细节（与 field.js 一致）

### 3.1 锚点层

- 唯一密度变量 **N = 每 km² 中心数**；格距 **L = 1000 / √N**（N=1 → L=1000 格；N=16 → L=250 格）。
- 格坐标 **(i,j) = (⌊x/L⌋, ⌊z/L⌋)**，向下取整（负坐标必须 floor，不能用截断除法）。
- 每格 **恰好 1 个锚点**：
  - 格心 + 每轴抖动 ∈ [−0.3L, +0.3L]（即锚点在格中央 0.6L 子方块内，距格边 ≥ 0.2L）；
  - 抖动由哈希 `h(seed, dimension, i, j, 用途标签)` 给出。
- 性质：无限、局部有限；密度**精确** = 1/L² = N/10⁶ 个/格²（不是期望）；无重合；无区块接缝。
- 限制：不保证锚点间最小间距，大 κ 时巢域可重叠、局部瞬时密度会波动。

### 3.2 巢域层

- **R_c = κ · L · σ_c**，其中 κ = 0.35（默认设计常量），σ_c ∈ [0.85, 1.15] 由哈希给出；R_max = 1.15·κL。
- 不变式：**|P(c,t) − A_c| ≤ R_c**（任意 t）。
- 查询局部性：若 t 时刻中心在 p 的 r0 内，则其锚点必在 p 的 R_max + r0 内。
- 查询邻域半宽：**m = ⌊(R_max + r0)/L + 0.8⌋**；默认参数（N=1、κ=0.35、r0=4）下 m=1，即 **3×3 = 9 个候选格**。
- 覆盖率（观感量）：巢域扫过面积 ≈ π(0.72κ)²。κ=0.35 → 约 20%；κ=0.7 → 约 80%；κ≈0.78 起全图无死角。

### 3.3 轨迹层

每中心有自己的时钟与相位，避免全世界同时换向的"心跳"：

- 段长 **T_c = 1.3·R_c / v̄**（v̄ 默认 0.29 格/tick；T ∝ R 保证不同密度下线速度一致）；
- 相位 τ_c（哈希 ∈ [0, T_c)）；
- 段号 **e = ⌊(t + τ_c)/T_c⌋**，段内相位 **u = (t + τ_c)/T_c − e ∈ [0,1)**（负 tick 由 floor 保证正确）。

目标点（二维低差异序列，面积均匀铺满巢域）：

- 半径相位：`u_e = frac(e·α + β_c)`，α = 1697/4096 ≈ 0.4143（≈√2−1）；
- 角度相位：`v_e = frac(e·γ + η_c)`，γ = 2531/4096 ≈ 0.6179 转（黄金角附近；须在 (0.5, 0.75) 且远离 0.5）；
- **W_c(e) = A_c + 0.72·R_c·√u_e · (cos 2πv_e, sin 2πv_e)**；
- 方向用**硬编码的 1024 项 Q15 定点单位向量表**查表，运行时零三角函数。

位置：对 W(e−1)、W(e)、W(e+1)、W(e+2) 做 **Catmull–Rom 插值**（段内相位 u）。

**有界性证明**：把一段 Catmull–Rom 写成三次 Bézier，四个控制点距锚点 ≤ 0.72R_c + (1/3)·(2·0.72R_c)/2 = 0.96R_c；Bézier 曲线在凸包内 ⇒ |P − A| ≤ 0.96R_c < R_c。

### 3.4 防抖动（R2）

抖动的定义：时间尺度与空间尺度同时很小的往复。本设计的结构性保证：

1. **时间下界**：最短时间尺度是 T_c（默认约 1600 tick = 80 s），T_c 内无随机事件、无高频噪声。
2. **空间下界**：目标点低差异构造保证每段弦长 ≥ 0.64R_c（默认约 225 格）；中心每段至少移动两百多格。
3. **速度下界**：平均速度 ≈ 0.28 格/tick，不存在随机停顿。
4. **切线非退化**：样条切线长度有正下界（约 0.3R_c），不会在目标点停顿/掉头。
5. **访问点等分布**：二维 Kronecker 序列让目标点面积均匀铺满巢域，不会长期困在一片扇区。
6. **有界领地**：不会漂走不回来，也不会在边界反弹聚集。

### 3.5 双层（必选，默认开启）

- **双层是产品的必选项**：大尺度游走只能靠层级（单层把 κ 调大只会让查询邻域和接缝一起变大），因此默认就开双层，不再作为可选附加。
- 粗层 = 同一套算法在 **k = coarseCells 倍尺度**上的一个实例（默认 k=8）；粗层格距 L_hi = k·L，粗层领地半径由 coarseKappa（默认 0.3）控制。
- 只取粗层的**位移向量**：`v_B(t) = 粗中心位置 − 粗锚点`。
- 归属**静态**：细锚点落在哪个粗格 B，就加哪个粗格的 v_B（不能按当前位置动态归属，否则会瞬移）。
- 位置：**P = P_细 + v_B**；有界 `|P − A| ≤ R_细 + R_粗`。
- 参数：**`layers` 默认为 2（必选）**；显式 `layers: 1` 只保留给单层对照/测试，不作为产品配置。demo 默认就是双层。
- 代价：
  - 查询/枚举要按 R_细 + R_粗 扩张，检测成本上升（实测 k=4、N=16 时单次检测 2.0 µs → 36.2 µs，约 18×）；
  - 粗格边界是"分片常数位移"，会出现密度接缝（带宽约 |Δv| ≤ 2R_粗）；本次只做最基础版，未做边界平滑；
  - 粗层漂移仍是有界的，不是真正的无界迁徙。

## 4. 查询原语与复杂度

**实现（field.js）**：

| 接口 | 返回 | 复杂度 |
|---|---|---|
| `create(options)` | field 对象 | 构造 O(1) |
| `field.home(i,j)` | `{i,j,x,z,r}` 锚点与领地半径 | O(哈希) |
| `field.centerAt(tick,i,j)` | `{i,j,x,z}` 该中心在整数刻的位置 | O(1) |
| `field.centersInRect(tick,minX,minZ,maxX,maxZ)` | 位置落在矩形内的中心数组（按 i、j 升序） | O(面积 × 密度) |
| `field.exists(tick,x,z,r0)` | `{exists, centers}`，r0 默认 4 | O(1)（默认 9 格 + 剪枝） |
| `field.lit(tick,i,j)` | `{lit, elapsed, startTick}` | O(1)（2 次哈希） |

**关键性质**：任何单点判定的代价与地图大小、中心总数、世界已运行时长无关；不需要中心状态、区块加载状态或网络同步。

**默认参数下的单次存在性查询**（N=1）：最多 9 个候选中心，锚点剪枝后平均 0.5 个，需一次轨迹求值。

## 5. 确定性工程铁律

1. **哈希**：32 位 splitmix/murmur 风格强混合（`Math.imul` 精确整数运算），输入 = 种子高低 32 位 + 维度 + 格坐标 + 用途标签；**每种用途单独一次哈希**，不复用同一个随机值；禁止 `Math.random` / `Date` / `ThreadLocalRandom` / 对象身份哈希。
2. **浮点**：只用 IEEE-754 的 `+ − × ÷` 与 `sqrt`（正确舍入）；**运行时禁止 sin/cos/tan/atan2/pow/exp/log/hypot/cbrt/fma**（跨 JVM/CPU 位一致无保证）。方向用硬编码定点表（1024 项 Q15），不要在运行时用三角函数生成表。
3. **坐标**：格坐标一律向下取整（floor）；负坐标、负 tick 必须专门测试。
4. **时间**：取世界创建以来的总游戏刻（gameTime 语义），不受 `/time set` 影响；不要用 dayTime（会 24000 回绕、可被指令修改、睡觉快进）。
5. **维度**：维度 id 混入哈希 ⇒ 各维度独立中心场。
6. **配置**：密度用整数（每 km² 个数）；κ、段长系数、方向表版本、算法版本都要进"配置指纹"，建世界时固化；改配置会让全场重排。
7. **范围**：数学支持 64 位，MC 世界边界约 ±3×10⁷ 格，实测在大坐标下正常。
8. **存档**：不保存任何中心状态，只需要种子、配置快照、当前 tick。

## 6. 参数与默认值

| 符号 | 含义 | 默认 | 说明 |
|---|---|---|---|
| N | 每 km² 中心数（唯一密度变量） | 1 | L = 1000/√N |
| κ | 领地半径 / 格距 | 0.35 | 决定覆盖率与查询邻域 |
| v̄ | 平均游走速度（格/tick） | 0.29 | 段长 T = 1.3R/v̄ |
| r0 | 存在性判定半径 | 4 格 | 建议 ≪ L |
| layers | 层数（双层为必选） | 2 | 默认 2；1 仅对照/测试 |
| coarseCells | 粗层格距倍数 k | 8 | 仅双层 |
| coarseKappa | 粗层 κ | 0.3 | 仅双层 |
| litDuration | 点亮时长 D（tick） | 240（12 s） | 固定时长 |
| litChance | 每时隙中签概率 p | 0.35 | 实际亮灯占比 ≈ p(1−p) |
| motionStep | 中心位置计算步长 | 200 tick（10 s） | Java 实现；步内位置恒定，不逐 tick 计算 |
| disasterDuration | 天灾持续时长 | 60 s（1200 tick） | Java config：`disasterDurationSeconds` |
| disasterRadiusChunks | 影响半径（区块） | 4 | Java config；区块中心距离判定 |

示例：N=1 时 L=1000、R≈350、T≈1569 tick；N=16 时 L=250、R≈88（最大 101）、T≈392 tick。扫过覆盖率只由 κ 决定（κ=0.35 时约 20%）。

## 7. 演进决策记录

### 7.1 巢域重叠（κ 调大）

- 用户观察："每个中心只在自己区域晃"。
- 结论：**κ 是最直接的观感旋钮，而且到 κ≈1.03 之前查询仍是 3×3 九格**（m=⌊1.15κ+0.8+r0/L⌋）。
- 实测（N=16）：κ=0.35 → 覆盖 20%、游走直径 126 格；κ=0.7 → 覆盖 80%、直径 252 格；κ=1.0 → 覆盖 163%、直径 360 格；三档查询都还是 9 格。
- 代价：地盘划分消失、同地点可能被多个中心覆盖（天灾归属需规则）、全图无死角后玩法难度上升。
- 未改动默认值；需要更"自由"的观感时把 κ 调到 0.7~0.8。

### 7.2 双层（必选，默认开启）

- 用户想法：叠加一个更大尺度的"巢"，把它的位移向量加到其范围内所有中心上。
- 结论：可行，本质是**层级位移场**；绝对游走尺度可放大数倍到数十倍而查询仍是 O(1)，但每层漂移必须 ≤ 该层格距，且层级间有接缝、查询要按总位移扩张。
- 决策：**双层是必选项**，默认开启；单层只保留给对照/测试与兼容。
- 实现：见 §3.5；默认开启后，检测成本与接缝是首要优化对象（见 §9、§11）。

### 7.3 随机点亮（R4）

- 用户需求：随机点亮、固定时长、要能同时得到"已经亮了多久"。
- 结论：**错相时隙 + 互斥点灯**：
  - 每中心相位 φ_c ∈ [0, D)，时隙 s = ⌊(t+φ_c)/D⌋，进度 local ∈ [0, D)；
  - 本时隙中签（u_s < p）**且**上一时隙未中签才点亮 ⇒ 每次恰好持续 D、两次之间至少暗 D；
  - 因此 `elapsed = local` 精确成立，`startTick = t − elapsed`；
  - 返回 `{lit, elapsed, startTick}`，O(1)、无状态、支持负 tick；
  - 实际点亮占比 = p(1−p)（p=0.35 时理论 0.2275，实测 0.2269–0.2284）。
- 渲染：点亮中心显示绿色（`#00b000`），其余红色；demo 已生效。实际亮灯占比 = p(1−p)（理论 0.2275；实测 0.2269–0.2284）。

### 7.4 天灾事件与加载范围（R5，已决策、未实现）

- 用户指出的问题：天灾影响是圆、玩家加载范围有限；若天灾中心不在加载范围内，本应在玩家处生效的天灾会被漏掉。
- 结论（详见 §8）：**把"中心推动"改成"玩家/加载区拉取"**；中心本身是纯函数，不会因未加载而停摆，漏检只发生在"结算被绑到被加载的中心"时。

## 8. 天灾事件设计（决策稿，结算层尚未实现）

### 8.1 事件表也做成纯函数

- 时隙 Δ（例如 1200 tick）、每中心相位、每时隙哈希；哈希决定：是否触发、灾种、时长（≤Δ，避免重叠）、影响半径。
- 用"本时隙中签且上一时隙未中签"保证事件之间至少隔 Δ，行为与点亮同构。
- 查询：给定 tick 与中心 id ⇒ 是否有灾、startTick、elapsed、remaining、radius、kind（O(1)，无状态，支持负 tick，读档/回滚/跨维度一致）。

### 8.2 拉取式结算

每 tick（或每 N tick）：

1. 以每个玩家/每块已加载区域为锚点，用 `centersInRect` 查询周围 **R_fx** 内所有中心的位置——纯几何查询，不需要这些中心所在区块被加载；
2. 对每个命中中心查事件表；
3. 事件圆与加载区/玩家相交时，只对"已加载且在圆内"的部分施加效果。

这样"中心在加载范围外、圆覆盖玩家"会被第 1 步查到；玩家永远在加载区，所以玩家侧不会漏。

### 8.3 未加载区域不追溯（关键取舍）

- 瞬时效果（伤害、天气、刷怪、光照）只在加载区执行；
- 永久方块改变只发生在事件发生时**已加载**的区块；玩家第一次到达的区块不补生成"他不在场时发生过的天灾痕迹"。
- 理由：追溯等于对每个区块评估"历史上所有天灾"，历史长度无界，会破坏 O(1) 与确定性（与有界性命题同源）。
- 若产品需要"世界到处有灾痕"：把永久灾痕做成**独立的确定性灾痕场**（按区块/坐标哈希），与事件表解耦；加载顺序不影响外观，但灾痕与玩家亲眼见过的天灾不是同一批事件。

### 8.4 区块级取整

- 影响半径按区块向下取整：**k = ⌊R_fx / 16⌋**；实际影响区 = (2k+1)² 个区块（方形）或约 πk² 个区块（圆形）。
- 检测区 = 加载区外扩 k 个区块 = **(21+2k)² 个区块**（加载半径 10）。
- 建议效果按**区块聚合**处理（每个已加载区块每 tick 最多一次），成本上界 = 已加载区块数 × 每区块成本，与事件数量无关。

### 8.5 多玩家 / 多维度

- 按每个玩家的矩形并集查询、按中心 id 去重；不同维度独立；
- 玩法判定用 simulation distance，纯视觉用 view distance；
- 玩家分散时成本按"互不相邻的区域数"线性增长，不按玩家数。

### 8.6 被否掉的方案

| 方案 | 否掉原因 |
|---|---|
| 给所有中心 forceload | 中心无限多，做不到 |
| 中心只在玩家附近生成/存在 | 破坏"种子+坐标唯一"，读档/多玩家不一致 |
| 状态机记录"事件已结算" | 回档、多玩家、跨维度不同步；纯函数事件表天然幂等 |
| 只在中心所在区块加载时才掷骰子 | 就是被发现的漏检 |
| 逐方块施加效果 | 成本爆炸（见 §9） |

## 9. 性能估算（实测 + 公式）

**口径**：区块 16；加载半径 10 → 21×21=441 区块=336×336 格=0.113 km²；影响按区块取整 k=⌊R_fx/16⌋；1 tick=50 ms。

### 9.1 检测成本（当前 field.js 实测，Node v24）

> 默认配置现在是**双层**：k=4、N=16 时单次检测约 **36.2 µs**（单层对照 2.0 µs，约 18×，因为要外扩 R_粗≈690 格）。下表单层数据仅作对照。

| N | k | 检测区（区块） | 期望中心数 | 单次 `centersInRect`（单层对照） |
|---|---|---|---|---|
| 1 | 0 | 441 | 0.11 | 0.88 µs |
| 1 | 4 | 841 | 0.22 | 0.41 µs |
| 1 | 8 | 1369 | 0.35 | 0.49 µs |
| 16 | 0 | 441 | 1.81 | 2.07 µs |
| 16 | 4 | 841 | 3.44 | 2.17 µs |
| 16 | 8 | 1369 | 5.61 | 2.15 µs |

辅助：`lit()` 0.096 µs、`home()` 0.062 µs、`centerAt()` 0.141 µs。（单次检测受 JIT 与测量噪声影响，±20% 以内不必在意；量级结论稳定。）

**双层**：k=4、N=16 时检测 2.0 µs → **36.2 µs**（约 18×，因为要外扩 R_粗≈690 格）。双层已是默认，**粗层预筛是下一步的首要优化**（候选粗格预筛可把检测拉回个位数 µs 量级）。

### 9.2 效果结算成本

受影响区块数：k=0→1、1→9、2→25、4→81、8→289（方形；圆形约为 πk²）。只处理已加载且在圆内的部分，上限 441 区块。

设每区块效果成本 c ≈ 0.5–2 µs（区块级操作：遍历实体、天气、抽样方块）：

- 单次事件 k=4：81×c ≈ **40–160 µs/tick**；
- 按区块聚合的最坏上界：441×c ≈ **0.22–0.88 ms/玩家区域/tick**；
- 事件频率示例（Δ=1200、p=0.25、时长 200 tick）：单中心占空比 ≈4.2%，检测区 3.4 个中心 ⇒ 同时事件 ≈0.14 个 ⇒ 平均效果 ≈ **6–23 µs/玩家区域/tick**。

### 9.3 汇总

| 场景 | 检测 | 效果（典型） | 合计 | 占 50ms tick |
|---|---|---|---|---|
| **双层 1 玩家（默认，N=16,k=4）** | ~36 µs | 6–23 µs | ~42–59 µs | 0.08–0.12% |
| **双层 20 玩家（默认）** | ~0.72 ms | 0.12–0.46 ms | 0.85–1.2 ms | 1.7–2.4% |
| 单层 20 玩家（对照） | ~40 µs | 0.12–0.46 ms | 0.16–0.5 ms | 0.3–1% |
| 最坏（441 区块全受灾，20 玩家，双层） | ~0.72 ms | 4.4–17.6 ms | 5.1–18.3 ms | 10–37%（应避免） |

**结论**：纯函数查询本身开销可忽略；真正决定开销的是"区块取整后的受影响区块数"与"每区块效果成本"；**绝不能逐方块施加效果**（k=4 时 81 区块 × 256 格 ≈ 2 万次方块操作/事件/tick）。区块取整的台阶很值钱：R_fx=63（k=3，49 区块）比 R_fx=64（k=4，81 区块）少约 40% 成本。

| 文件 | 内容 |

实现约束：

- **只检查已加载区块**：区块未在缓存中时 `status()` 返回 `null`，不会凭空求值；`/disaster ison` 对未加载区块返回提示。
- **每 10 s 才算一次运动**：`motionStep = floorDiv(gameTime, 200)`，位置在步内恒定；步变化时清空位置缓存。事件表仍按 tick 精确判定。
- **坐标/影响粒度**：中心位置用双精度方块坐标；影响半径用区块数（默认 4），区块中心落在半径内即受影响；候选格按 `R_细 + R_粗 + 影响半径` 扩张，成本与地图大小无关。
- **事件表**：时隙长度 = `disasterDurationSeconds × 20`，每中心独立相位；时隙中签（固定 p=0.35）且上一时隙未中签才生效，因此每次恰好持续配置时长，之后至少空一个时隙。
- **配置**：`kappa`（巢域）、`disasterDurationSeconds`、`disasterRadiusChunks`；粗层 `coarseCells=8`、`coarseKappa=0.3` 为当前设计常量。
- **未实现**：任何天灾效果、灾种、逐事件半径、拉取式结算。

验证：独立场测试（确定性、步内恒定/跨步变化、负 tick、区块覆盖与暴力枚举一致、事件时长与间隔）通过；专用服务器 RCON 实测 `/disaster ison`：未加载区块返回提示，force-load 后返回活动中心与剩余时间，移除 force-load 并卸载后恢复提示。

## 11. 已知限制

1. **有界**：中心永远在锚点 R 内；双层只是把笼子做大，不是无界迁徙。
2. **双层接缝**：粗格边界的分片常数位移会产生密度带；未做平滑。
3. **双层查询成本（默认）**：当前实现按总位移扩张枚举，检测成本约为单层 18×（k=4、N=16 时 36 µs/玩家/tick）；粗层预筛是下一步优化项。
4. **未加载不追溯**：这是取舍，不是 bug；若需要"全图灾痕"，用独立灾痕场。
5. **点亮时长语义**：实际亮灯占比是 p(1−p)，不是 p；调参时注意。
6. **渲染验证**：沙箱内无法启动 Chromium（mojo 命名管道被拒）；前端用假 DOM 回放真实 app.js 验证，另有桌面 Edge 人工确认。
7. **性能数字是 Node JS 量级**：Java 模组可能更快或同量级，量级结论不变。
