## 0. 一句话

把"天灾中心"写成**静态锚点 + 有界巢域 + 低差异航点样条**的纯函数时空场：给定（世界种子、游戏刻、坐标）即可 O(1) 判定某处此刻有没有中心、位置在哪，以及是否有天灾正在生效——不需要逐刻模拟、不保存任何需要持久化的中心状态（只有可随时重建的内存派生缓存，见 §10.8）。

## 2. 核心模型：纯函数时空场

### 2.1 为什么必须"有界"

- R3 要求中心位置写成时间的纯函数 P(c,t)，不能依赖历史状态；
- R1 要求中心无限，所以"判定 p 处有没有中心"只能由 p 附近的**静态局部信息**产生候选；
- 若每个中心都能各自无界漂移，世界运行越久，任意远处的中心都可能出现在 p，候选集合半径随 t 无界增长 ⇒ O(1) 查询不成立。

> **有界性命题**：在"无限时间 + 无限中心 + O(1) 点查询"下，每个中心相对静态锚点的位移必须有与时间无关的上界 R，且 R = O(L)（L 为锚点格距）。唯一例外是"全体中心共享同一个随时间变化的坐标变换"（整体平移/旋转），因为查询只需一次逆变换。

所以"巢域"不是美术妥协，而是可计算性要求；这也决定了"大范围游走"只能靠**分层/放大尺度**，不能靠单个中心无界漂移。

### 2.2 三层结构

- **L1 锚点层**：世界切成 L×L 的格，每格恰好 1 个锚点，位置哈希抖动。
- **L2 巢域层**：每个中心永远位于其锚点周围半径 R 的圆盘内。
- **L3 轨迹层**：在巢域内取一串低差异目标点，用 C¹ 的 Catmull–Rom 样条连成轨迹；位置是段号与段内相位的函数。

## 3. 算法细节（与 field.js 一致）

### 3.1 锚点层

- 唯一密度变量 **N = 每 km² 中心数**；格距 **L = 1000 / √N**（N=1 → L=1000 格；N=16 → L=250 格）。
- 格坐标 **(i,j) = (⌊x/L⌋, ⌊z/L⌋)**，向下取整（负坐标必须 floor，不能用截断除法）。
- 每格 **恰好 1 个锚点**：
  - 格心 + 每轴抖动 ∈ [−0.3L, +0.3L]（即锚点在格中央 0.6L 子方块内，距格边 ≥ 0.2L）；
  - 抖动由哈希 `h(seed, dimension, i, j, 用途标签)` 给出。
- 性质：无限、局部有限；密度**精确** = 1/L² = N/10⁶ 个/格²（不是期望）；无重合；无区块接缝。
- 限制：不保证锚点间最小间距，大 κ 时巢域可重叠、局部瞬时密度会波动。

### 3.2 巢域层

- **R_c = κ · L · σ_c**，其中 κ = 0.35（默认设计常量），σ_c ∈ [0.85, 1.15] 由哈希给出；R_max = 1.15·κL。
- 不变式：**|P(c,t) − A_c| ≤ R_c**（任意 t）。
- 查询局部性：若 t 时刻中心在 p 的 r0 内，则其锚点必在 p 的 R_max + r0 内。
- 查询邻域半宽：**m = ⌊(R_max + r0)/L + 0.8⌋**；默认参数（N=1、κ=0.35、r0=4）下 m=1，即 **3×3 = 9 个候选格**。
- 覆盖率（观感量）：巢域扫过面积 ≈ π(0.72κ)²。κ=0.35 → 约 20%；κ=0.7 → 约 80%；κ≈0.78 起全图无死角。

### 3.3 轨迹层

每中心有自己的时钟与相位，避免全世界同时换向的"心跳"：

- 段长 **T_c = 1.3·R_c / v̄**（v̄ 来自 Java config `walkSpeedBlocksPerTick`，默认 0.145 格/tick；T ∝ R 保证不同密度下线速度一致）；
- 相位 τ_c（哈希 ∈ [0, T_c)）；
- 段号 **e = ⌊(t + τ_c)/T_c⌋**，段内相位 **u = (t + τ_c)/T_c − e ∈ [0,1)**（负 tick 由 floor 保证正确）。

目标点（二维低差异序列，面积均匀铺满巢域）：

- 半径相位：`u_e = frac(e·α + β_c)`，α = 1697/4096 ≈ 0.4143（≈√2−1）；
- 角度相位：`v_e = frac(e·γ + η_c)`，γ = 2531/4096 ≈ 0.6179 转（黄金角附近；须在 (0.5, 0.75) 且远离 0.5）；
- **W_c(e) = A_c + 0.72·R_c·√u_e · (cos 2πv_e, sin 2πv_e)**；
- 方向用**硬编码的 1024 项 Q15 定点单位向量表**查表，运行时零三角函数。

位置：对 W(e−1)、W(e)、W(e+1)、W(e+2) 做 **Catmull–Rom 插值**（段内相位 u）。

**有界性证明**：把一段 Catmull–Rom 写成三次 Bézier，四个控制点距锚点 ≤ 0.72R_c + (1/3)·(2·0.72R_c)/2 = 0.96R_c；Bézier 曲线在凸包内 ⇒ |P − A| ≤ 0.96R_c < R_c。

### 3.4 防抖动（R2）

抖动的定义：时间尺度与空间尺度同时很小的往复。本设计的结构性保证：

1. **时间下界**：最短时间尺度是 T_c（默认约 3200 tick = 160 s），T_c 内无随机事件、无高频噪声。
2. **空间下界**：目标点低差异构造保证每段弦长 ≥ 0.64R_c（默认约 225 格）；中心每段至少移动两百多格。
3. **速度下界**：平均速度 ≈ 0.14 格/tick，不存在随机停顿。
4. **切线非退化**：样条切线长度有正下界（约 0.3R_c），不会在目标点停顿/掉头。
5. **访问点等分布**：二维 Kronecker 序列让目标点面积均匀铺满巢域，不会长期困在一片扇区。
6. **有界领地**：不会漂走不回来，也不会在边界反弹聚集。

### 3.5 双层（必选，默认开启）

- **双层是产品的必选项**：大尺度游走只能靠层级（单层把 κ 调大只会让查询邻域和接缝一起变大），因此默认就开双层，不再作为可选附加。
- 粗层 = 同一套算法在 **k = coarseCells 倍尺度**上的一个实例（默认 k=8）；粗层格距 L_hi = k·L，粗层领地半径由 coarseKappa（默认 0.3）控制。
- 只取粗层的**位移向量**：`v_B(t) = 粗中心位置 − 粗锚点`。
- 归属**静态**：细锚点落在哪个粗格 B，就加哪个粗格的 v_B（不能按当前位置动态归属，否则会瞬移）。
- 位置：**P = P_细 + v_B**；有界 `|P − A| ≤ R_细 + R_粗`。
- 参数：**`layers` 默认为 2（必选）**；显式 `layers: 1` 只保留给单层对照/测试，不作为产品配置。demo 默认就是双层。
- 代价：
  - 查询/枚举要按 R_细 + R_粗 扩张，检测成本上升（实测 k=4、N=16 时单次检测 2.0 µs → 36.2 µs，约 18×）；
  - 粗格边界是"分片常数位移"，会出现密度接缝（带宽约 |Δv| ≤ 2R_粗）；本次只做最基础版，未做边界平滑；
  - 粗层漂移仍是有界的，不是真正的无界迁徙。

## 4. 查询原语与复杂度

**实现（field.js）**：

| 接口 | 返回 | 复杂度 |
|---|---|---|
| `create(options)` | field 对象 | 构造 O(1) |
| `field.home(i,j)` | `{i,j,x,z,r}` 锚点与领地半径 | O(哈希) |
| `field.centerAt(tick,i,j)` | `{i,j,x,z}` 该中心在整数刻的位置 | O(1) |
| `field.centersInRect(tick,minX,minZ,maxX,maxZ)` | 位置落在矩形内的中心数组（按 i、j 升序） | O(面积 × 密度) |
| `field.exists(tick,x,z,r0)` | `{exists, centers}`，r0 默认 4 | O(1)（默认 9 格 + 剪枝） |

**关键性质**：任何单点判定的代价与地图大小、中心总数、世界已运行时长无关；单点查询本身不需要中心状态、区块加载状态或网络同步（服务层的已加载区块候选与开始区块缓存都是可重建的派生数据，见 §10.8）。

**默认参数下的单次存在性查询**（N=1）：最多 9 个候选中心，锚点剪枝后平均 0.5 个，需一次轨迹求值。

## 5. 确定性工程铁律

1. **哈希**：32 位 splitmix/murmur 风格强混合（`Math.imul` 精确整数运算），输入 = 种子高低 32 位 + 维度 + 格坐标 + 用途标签；**每种用途单独一次哈希**，不复用同一个随机值；禁止 `Math.random` / `Date` / `ThreadLocalRandom` / 对象身份哈希。
2. **浮点**：只用 IEEE-754 的 `+ − × ÷` 与 `sqrt`（正确舍入）；**运行时禁止 sin/cos/tan/atan2/pow/exp/log/hypot/cbrt/fma**（跨 JVM/CPU 位一致无保证）。方向用硬编码定点表（1024 项 Q15），不要在运行时用三角函数生成表。
3. **坐标**：格坐标一律向下取整（floor）；负坐标、负 tick 必须专门测试。
4. **时间**：取世界创建以来的总游戏刻（gameTime 语义），不受 `/time set` 影响；不要用 dayTime（会 24000 回绕、可被指令修改、睡觉快进）。
5. **维度**：维度 id 混入哈希 ⇒ 各维度独立中心场。
6. **配置**：密度用整数（每 km² 个数）；κ、段长系数、方向表版本、算法版本都要进"配置指纹"，建世界时固化；改配置会让全场重排。
7. **范围**：数学支持 64 位，MC 世界边界约 ±3×10⁷ 格，实测在大坐标下正常。
8. **存档**：不保存任何中心状态，只需要种子、配置快照、当前 tick；运行期派生的开始区块缓存不写入存档，重启后可重建。

## 6. 参数与默认值

| 符号 | 含义 | 默认 | 说明 |
|---|---|---|---|
| N | 每 km² 中心数（唯一密度变量） | 1 | L = 1000/√N |
| κ | 领地半径 / 格距 | 0.35 | 决定覆盖率与查询邻域 |
| v̄ | 平均游走速度（格/tick） | 0.145 | Java config：`walkSpeedBlocksPerTick`；段长 T = 1.3R/v̄ |
| r0 | 存在性判定半径 | 4 格 | 建议 ≪ L |
| layers | 层数（双层为必选） | 2 | 默认 2；1 仅对照/测试 |
| coarseCells | 粗层格距倍数 k | 8 | 仅双层 |
| coarseKappa | 粗层 κ | 0.3 | 仅双层 |
| motionStep | 中心位置与动态半径计算步长 | 20 tick（1 s） | Java 实现；步内位置恒定，不逐 tick 计算；采样频率与速度独立 |
| disasterDuration | 天灾总时长 D | 600 s（12000 tick） | Java config：`disasterDurationSeconds`；包含预警 |
| disasterWarning | 固定预警时长 W | 60 s（1200 tick） | 生命周期常量，不随 D 缩放 |
| disasterRadiusChunks | 最大影响半径 R | 8 区块（128 格） | Java config；当前帧半径按生命周期公式派生，查询按 R 扩张 |
| surfaceDisasterTickSpeed | 地表天灾刻每区块每 tick 样本数 | 2 | Java config；合法域 0–32，0 关闭；不属于中心场指纹，不改变中心/事件 |
| randomDisasterTickSpeed | 随机天灾刻每区块每 tick 样本数 | 3 | Java config；合法域 0–32，0 关闭；不属于中心场指纹，不改变中心/事件 |

派生：增长 `G = D/2 = 300 s = 6000 tick`，衰退 `F = D − W − G = 240 s = 4800 tick`。合法域必须满足 **`D > 2W`**，否则 F ≤ 0。生命周期与半径公式见专项文档；半径只影响覆盖判定，不改变中心位置算法。

两个天灾刻速度只控制选中样本数，不是每个 section 的数量；它们不影响 §10.4 的配置指纹，也不会重排中心或事件。灾种映射配置 `disasterTypes.biomeToType` 只决定灾种，支持精确 `biomeId=typeId` 与标签 `#tagId=typeId` 两种条目；优先级为精确群系覆盖 > 标签覆盖 > 内置 `dummy`，多个标签命中同一群系时按配置数组从前到后首个命中生效，与标签条目和精确条目的相对位置无关。它同样不属于中心场配置指纹，不改变中心位置、事件表或 `FieldParams`。

示例：N=1 时 L=1000、R≈350、T≈3138 tick；N=16 时 L=250、R≈88（最大 101）、T≈790 tick。扫过覆盖率只由 κ 决定（κ=0.35 时约 20%）。下文的 `k` 若未特别说明，指**受影响区块半径**，当前默认最大 `k = 8`。

## 7. 演进决策记录

### 7.1 巢域重叠（κ 调大）

- 用户观察："每个中心只在自己区域晃"。
- 结论：**κ 是最直接的观感旋钮，而且到 κ≈1.03 之前查询仍是 3×3 九格**（m=⌊1.15κ+0.8+r0/L⌋）。
- 实测（N=16）：κ=0.35 → 覆盖 20%、游走直径 126 格；κ=0.7 → 覆盖 80%、直径 252 格；κ=1.0 → 覆盖 163%、直径 360 格；三档查询都还是 9 格。
- 代价：地盘划分消失、同地点可能被多个中心覆盖（天灾归属需规则）、全图无死角后玩法难度上升。
- 未改动默认值；需要更"自由"的观感时把 κ 调到 0.7~0.8。

### 7.2 双层（必选，默认开启）

- 用户想法：叠加一个更大尺度的"巢"，把它的位移向量加到其范围内所有中心上。
- 结论：可行，本质是**层级位移场**；绝对游走尺度可放大数倍到数十倍而查询仍是 O(1)，但每层漂移必须 ≤ 该层格距，且层级间有接缝、查询要按总位移扩张。
- 决策：**双层是必选项**，默认开启；单层只保留给对照/测试与兼容。
- 实现：见 §3.5；默认开启后，检测成本与接缝是首要优化对象（见 §9、§11）。

### 7.3 天灾事件与加载范围（R5，拉取式查询、选中与灾种声明已实现；灾种效果与方块判断未实现）

- 用户指出的问题：天灾影响是圆、玩家加载范围有限；若天灾中心不在加载范围内，本应在玩家处生效的天灾会被漏掉。
- 结论（详见 §8）：**把"中心推动"改成"玩家/加载区拉取"**；中心本身是纯函数，不会因未加载而停摆，漏检只发生在"结算被绑到被加载的中心"时。
- 2026-10-29 生命周期决策：总时长 `D = 600 s = 12000 tick`，最大半径 `R = 8` 区块，固定预警 `W = 60 s = 1200 tick`；`G = D/2`、`F = D − W − G`，合法域 `D > 2W`。阶段用真实 tick，半径用全局 20 tick 运动帧（`e = motionTick − startTick`），增长 `ceil`、衰退 `floor`，不修正奇数 `R` 的不对称或 0 半径。预警黄色且无效果，增长/衰退红色且有效果，重叠时红色优先。详见《天灾生命周期与动态影响半径设计.md》。

## 8. 天灾事件设计（事件表、生命周期、快照、选中与灾种声明已实现；灾种映射/效果与方块判断尚未接入）

### 8.1 事件表也做成纯函数

- 时隙长度 = `D`（默认 12000 tick）、每中心相位、每时隙哈希；哈希只决定**是否触发**，**不再**决定时长与半径。灾种也不由时隙哈希决定：它应由**事件开始时中心所在区块的群系**经配置映射决定（未来接入）；本阶段只声明灾种与映射基建（§10.8），不读取开始区块群系、不执行灾种效果，事件表与 `FieldParams` 均不因灾种改变。
- 时长固定为配置 `D`，半径固定上限为配置 `R`，当前半径由 `startTick`、真实 `elapsed` 与 20 tick 运动帧派生，逐 tick 状态不保存。
- 用"本时隙中签且上一时隙未中签"保证事件之间至少隔一个时隙（即空闲至少 `D`）。
- 查询：给定 tick 与中心 id ⇒ `EventState`（`active`、`phase`、`startTick`、`elapsed`、`remaining`、`effectActive`、`radiusChunks`；配置最大半径另取），O(1)，无状态，支持负 tick，读档/回滚/跨维度一致。
- 阶段语义：`WARNING` 预警（黄色、无效果）、`GROWING` 增长（红色、有效果）、`DECAYING` 衰退（红色、有效果）。阶段用真实 tick；半径用运动帧，最多滞后 19 tick。

### 8.2 拉取式结算：天灾刻选中（已实现）

结算分两阶段：**选中**（本轮已接入）与**方块判断/效果执行**（未实现）。

选中阶段每个服务端 tick 执行一次，只遍历 `DisasterService` 已缓存的加载区块，不扫描全世界、不强加载区块：

1. 对每个已缓存区块，直接读取缓存的最大半径候选，用当前事件状态与当前半径过滤；只有至少一个 `EventState.effectActive()` 的中心当前覆盖该区块时才继续。遍历不构建过滤 List 或 `ChunkStatus`，并在同一遍已加载区块候选上维护每维度的活跃中心开始区块缓存（§10.8）；`WARNING` 或空闲不选。
2. 对通过筛选的区块，通过非加载的 chunk-source 查询取一次 `LevelChunk`（null 则跳过），再调用两类公开选择方法，两者每次均返回定长 `BlockPos[]`：
   - **地表天灾刻**（`surfaceDisasterTickSpeed`，默认 2）：在区块 16×16 列中哈希选 local x/z，y 直接取该 chunk 的 `WORLD_SURFACE` 高度图最上一格方块（`LevelChunk.getHeight` 已返回方块本身）；禁止纵向扫描。
   - **随机天灾刻**（`randomDisasterTickSpeed`，默认 3）：在整个区块的 16×16 列与 chunk 的建筑高度范围（`minBuildHeight` 起、不含 `maxBuildHeight`）内哈希选 x/y/z；不读高度图，不获取 `BlockState`。
3. 两类抽取相互独立，坐标由世界 seed、维度、真实 `gameTime`、区块坐标、用途标签与样本序号经现有 `Hash` 强混合派生；不使用 `Random`、`Math.random`、系统时间或可变状态；负 tick/负区块坐标按 floor/无符号语义处理。同一调用与不同 tick 之间都可能重复坐标，返回数组长度恰等于对应速度；速度 0 返回共享空数组。速度不是"每个 section 的数量"。
4. 选中结果**不缓存、不持久化**。本轮到此为止：未来由天灾系统检查坐标处方块再决定逻辑；当前不得读取方块状态来决定逻辑，也不执行任何方块/实体/天气/药水效果。

"中心在加载范围外、圆覆盖玩家"仍由每中心纯函数场表达；选中以已加载区块为锚点，玩家永远在加载区，所以玩家所在区块不会漏选。禁止逐中心 tick，也禁止追溯未加载区块。

### 8.3 未加载区域不追溯（关键取舍）

- 瞬时效果（伤害、天气、刷怪、光照）只在加载区执行；
- 永久方块改变只发生在事件发生时**已加载**的区块；玩家第一次到达的区块不补生成"他不在场时发生过的天灾痕迹"。
- 理由：追溯等于对每个区块评估"历史上所有天灾"，历史长度无界，会破坏 O(1) 与确定性（与有界性命题同源）。
- 若产品需要"世界到处有灾痕"：把永久灾痕做成**独立的确定性灾痕场**（按区块/坐标哈希），与事件表解耦；加载顺序不影响外观，但灾痕与玩家亲眼见过的天灾不是同一批事件。

### 8.4 区块级半径

- 影响半径直接以**区块数**配置（`disasterRadiusChunks`，默认最大 `R = 8`），不再从方块半径向下取整。当前帧整数半径 `r` 由生命周期公式给出（预警 4，增长 4→8，衰退 8→4，另见专项文档）。
- 实际影响区 = `(2r+1)²` 个区块（方形判定）或约 `πr²` 个区块（圆形观感）。
- 检测区 = 加载区外扩**最大半径** `R`，默认 **(21+2×8)² = 37² = 1369 个区块**；候选中心按 `R` 扩张后再用当前 `r` 过滤，禁止用 `r` 缩小候选范围。
- 天灾刻选中已按**区块聚合**（每个受有效效果覆盖的已加载区块每 tick 各选 2 个地表点与 3 个随机点，可配置为 0）；未来的方块判断与效果执行也必须沿用该粒度，成本上界 = 已加载区块数 × 每区块成本，与事件数量无关。

### 8.5 多玩家 / 多维度

- 按每个玩家的矩形并集查询、按中心 id 去重；不同维度独立；
- 玩法判定用 simulation distance，纯视觉用 view distance；
- 玩家分散时成本按"互不相邻的区域数"线性增长，不按玩家数。

### 8.6 被否掉的方案

| 方案 | 否掉原因 |
|---|---|
| 给所有中心 forceload | 中心无限多，做不到 |
| 中心只在玩家附近生成/存在 | 破坏"种子+坐标唯一"，读档/多玩家不一致 |
| 状态机记录"事件已结算" | 回档、多玩家、跨维度不同步；纯函数事件表天然幂等 |
| 只在中心所在区块加载时才掷骰子 | 就是被发现的漏检 |
| 逐方块施加效果 | 成本爆炸（见 §9） |

## 9. 性能估算（实测 + 公式）

**口径**：区块 16；加载半径 10 → 21×21=441 区块=336×336 格=0.113 km²；`k` 为当前帧**区块半径**（最大 `R = 8`），不再由方块半径取整；1 tick=50 ms。

### 9.1 检测成本（当前 field.js 实测，Node v24）

> 历史实测按当时的默认 `k=4`、`N=16`：单次检测约 **36.2 µs**（单层对照 2.0 µs，约 18×，因为要外扩 R_粗≈690 格）。`k` 在表中是区块半径；当前默认最大 `R=8` 对应 1369 区块检测区（表中 k=8 行），量级结论不变。下表为单层数据，仅作对照。

| N | k | 检测区（区块） | 期望中心数 | 单次 `centersInRect`（单层对照） |
|---|---|---|---|---|
| 1 | 0 | 441 | 0.11 | 0.88 µs |
| 1 | 4 | 841 | 0.22 | 0.41 µs |
| 1 | 8 | 1369 | 0.35 | 0.49 µs |
| 16 | 0 | 441 | 1.81 | 2.07 µs |
| 16 | 4 | 841 | 3.44 | 2.17 µs |
| 16 | 8 | 1369 | 5.61 | 2.15 µs |

辅助：`home()` 0.062 µs、`centerAt()` 0.141 µs。（单次检测受 JIT 与测量噪声影响，±20% 以内不必在意；量级结论稳定。）

**双层**：k=4、N=16 时检测 2.0 µs → **36.2 µs**（约 18×，因为要外扩 R_粗≈690 格）。双层已是默认，**粗层预筛是下一步的首要优化**（候选粗格预筛可把检测拉回个位数 µs 量级）。

### 9.2 效果结算成本

受影响区块数：k=0→1、1→9、2→25、4→81、8→289（方形；圆形约为 πk²）。只处理已加载且在圆内的部分，上限 441 区块。生命周期使 `k` 在4与8之间变化：预警4、增长4→8、衰退8→4。

天灾刻选中阶段另计：每个受有效效果覆盖的已加载区块每 tick 先取一次 `LevelChunk`，再各生成 2/3 个定长 `BlockPos[]`（默认值），只做哈希与高度图读取；未做运行时测量，量级判断不构成实测结论。方块判断与效果执行尚未实现。

设每区块效果成本 c ≈ 0.5–2 µs（区块级操作：遍历实体、天气、抽样方块）：

- 单次事件取最大 k=8：289×c ≈ **145–578 µs/tick**（历史默认 k=4 时为 40–160 µs）；
- 按区块聚合的最坏上界：441×c ≈ **0.22–0.88 ms/玩家区域/tick**；
- 事件频率示例（D=12000 tick、p=0.35）：单中心占空比 = p(1−p) ≈22.75%，检测区期望中心数约0.35（N=1，k=8）⇒ 同时事件约0.08个；按平均半径约6区块（约113区块）估算，平均效果约 **4–18 µs/玩家区域/tick**。该值为量级估算，不是实测。

### 9.3 汇总

| 场景 | 检测 | 效果（典型） | 合计 | 占 50ms tick |
|---|---|---|---|---|
| **双层 1 玩家（历史参考 N=16,k=4）** | ~36 µs | 6–23 µs | ~42–59 µs | 0.08–0.12% |
| **双层 20 玩家（历史参考）** | ~0.72 ms | 0.12–0.46 ms | 0.85–1.2 ms | 1.7–2.4% |
| 单层 20 玩家（对照） | ~40 µs | 0.12–0.46 ms | 0.16–0.5 ms | 0.3–1% |
| 最坏（441 区块全受灾，20 玩家，双层） | ~0.72 ms | 4.4–17.6 ms | 5.1–18.3 ms | 10–37%（应避免） |

**结论**：纯函数查询本身开销可忽略；真正决定开销的是"当前区块半径覆盖的区块数"与"每区块效果成本"；**绝不能逐方块施加效果**（k=8 时 289 区块 × 256 格 ≈ 7.4 万次方块操作/事件/tick）。整数半径仍有台阶：k=7 为 225 区块，k=8 为 289 区块，后者约多 28% 成本。

实现约束：

- **只检查已加载区块**：区块未在缓存中时 `status()` 返回 `null`，不会凭空求值；`/disaster ison` 对未加载区块返回提示。`/disaster locate` 是纯场查询，不受加载状态限制，但只扫描固定 24 圈中心网格，不枚举整个世界。
- **位置与半径共用 20 tick 运动帧**：`motionStep = floorDiv(gameTime, 20)`，位置和半径在步内恒定；步变化时清空缓存。事件阶段仍按真实 tick 精确判定；采样保持 20 tick；`walkSpeedBlocksPerTick` 默认 0.145，并由段长公式决定实际移动速度。
- **坐标/影响粒度**：中心位置用双精度方块坐标；最大影响半径以区块数配置（默认 8），当前帧半径 `radiusChunks` 由生命周期公式给出，区块中心落在当前半径内即受影响；候选格按 `R_细 + R_粗 + 最大半径` 扩张，成本与地图大小无关。禁止用当前半径缩小候选范围。
- **事件表与生命周期**：时隙长度 = `disasterDurationSeconds × 20`（默认 12000 tick），每中心独立相位；时隙中签（固定 p=0.35）且上一时隙未中签才生效，因此每次恰好持续配置时长，之后至少空一个时隙。`EventState` 的 `phase/effectActive/radiusChunks` 均由 `startTick`、`tick`、配置派生，不保存状态。
- **阶段与呈现**：`WARNING` 黄色、无效果；`GROWING`/`DECAYING` 红色、有效果；重叠时红色优先。阶段边界用真实 tick，半径跳变最多滞后 19 tick。
- **天灾刻选中**：每服务端 tick 只访问 `DisasterService` 已缓存的加载区块；`visitEffectCenters` 直接读缓存候选判断是否存在 `effectActive` + 当前半径命中的中心，不调用 `status()`/`currentHits()`，每 tick 热路径不新建过滤 List、`ChunkStatus` 或 `CenterHit`（跨运动帧仍按需 `evaluate`）；同一遍遍历已加载区块候选并维护开始区块缓存（§10.8），因此不以首个命中短路作为性能承诺。公开 `status()` 给命令的过滤语义不变。通过筛选的区块用非加载 `getChunkNow` 取一次 `LevelChunk`（null 跳过），再调用 `surface(LevelChunk, tick, samples)` / `random(LevelChunk, tick, samples)`，采样内不再查找区块。两类公开方法均返回定长 `BlockPos[]`，默认地表 2、随机 3，速度 0 返回共享空数组。抽取独立、允许重复；坐标确定性由 seed/维度/`gameTime`/区块/用途/样本序号派生，使用 `Hash` 与 `floorMod`/位运算，不用 `Random`、系统时间或可变状态。选中不读方块状态、不缓存、不持久化、不执行效果。
- **灾种与群系映射**：`DisasterTypes` 只声明 `dummy` / `snow_storm` 与未知回退，不执行效果。`disasterTypes.biomeToType` 为 COMMON 配置的字符串列表，默认空，支持两种条目：精确 `biomeId=typeId` 与标签 `#tagId=typeId`（标签为 `TagKey<Biome>`，数据包路径 `data/<ns>/tags/worldgen/biome/*.json`）。配置加载只校验元素为 String，不访问群系注册表与标签；服务器启动时由 `BiomeDisasterTypes.rebuild` 逐条解析语法并检查 `Registries.BIOME` 与群系标签，物化全群系表，默认全员 `dummy`，再应用覆盖。优先级为精确群系覆盖 > 标签覆盖 > 内置 `dummy`；多个标签命中同一群系时按配置数组从前到后首个命中生效，与标签条目和精确条目的相对位置无关；重复精确条目仍是后者覆盖前者。未知群系、未知标签、未知灾种与坏条目逐条警告并跳过，单条坏条目不会清空其他有效配置。映射不进入 `FieldParams`，不影响中心位置、事件表或配置指纹；本阶段不读取开始区块群系、不执行灾种效果。
- **活跃中心开始区块缓存**：每维度 `LevelState` 持有 `centerId → ActiveCenterStart` 的派生缓存，`centerId` 由 `gridX/gridZ` 组成（`DisasterField.centerId`）。每个服务端 tick 在已加载区块候选上维护：新出现的活跃中心以 `centerPositionUncached` 求 `startTick` 所属 20 tick 运动帧的位置，换算为开始区块并记录 `startTick`；事件结束或中心不再属于已加载候选集合时删除。不全世界扫描、不强加载区块、不持久化、不写入存档或网络快照，重启/换维度时重新建立；它只服务未来"开始区块群系 → 灾种"接入，本阶段不据此读取群系。
- **历史位置查询不污染缓存**：`centerPositionUncached(tick, i, j)` 只做纯位置求值，不读写 `fineCache` / `coarseCache`；查询历史帧（如事件开始帧）不会替换当前运动帧的位置缓存。开始区块是 20 tick 运动帧量化位置，不是真实 tick 精确位置，也不跟随中心当前位置。
- **配置**：`kappa`（巢域）、`walkSpeedBlocksPerTick`（默认 0.145 格/tick）、`disasterDurationSeconds`（默认 600 s / 12000 tick）、`disasterRadiusChunks`（默认 8）；`W = 1200 tick` 为生命周期常量，合法域 `D > 2W`；粗层 `coarseCells=8`、`coarseKappa=0.3` 为当前设计常量；天灾刻速度 `surfaceDisasterTickSpeed` 默认 2、`randomDisasterTickSpeed` 默认 3（0–32），不影响中心场配置指纹；`disasterTypes.biomeToType` 默认空（精确与标签两种条目），同样不影响中心场配置指纹。
- **未实现**：灾种效果、把效果自动绑定到灾难场、拉取式结算中的方块判断与效果执行（选中已接入，见 §10.7）；开始区块群系的运行时读取与类型接入待做；通用效果原语与调试命令见 §10.6。

命令用法：

- `/disaster debug viewdistance <chunks> [targets]`：`chunks` 取 2–32；
- `/disaster debug viewdistance reset [targets]`：恢复覆盖前视距；
- `/disaster debug effect <effect> <durationSeconds> [amplifier] [targets]`：注册表 effect id；秒 ×20 转 tick；`amplifier` 取 0–255，缺省 0；
- `/disaster debug fog <red> <green> <blue> [targets]`：各分量取 0–255；
- `/disaster debug fog clear [targets]`：恢复正常雾色渲染；
- `/disaster debug weather <rain|thunder|snow> [targets]`：让目标客户端强制显示降雨、雷雨或雪；三者都覆盖群系降水判定（`thunder` 同时为满降雨 + 满雷暴强度）；
- `/disaster debug weather stop [targets]`：停止强制天气显示，恢复服务端最近一次上报的天气。

约束与一致性：

- **玩家露天查询（2026-11-05）**：通用入口 `DisasterEffects.isPlayerExposed(UUID playerId)` 返回布尔值。在服务端线程调用，通过当前服务器的在线玩家列表解析 UUID，在玩家当前维度、眼睛所在方块调用原版 `canSeeSky`；采用原版天空光判定，不受昼夜、天气或客户端强制天气影响，也不额外逐方块扫描遮挡。透明屋顶等边界沿用原版天空光语义。`null` UUID、服务器未运行或玩家不在线时返回 `false`。仅查询，不施加任何效果、不改变中心场或配置指纹。
- **服务器权威**：视距/雾色都是客户端表现，但只由服务端校验参数后发 clientbound 载荷触发；服务端不读取也不直接修改客户端选项。
- **原值只保存一次**：客户端在第一次覆盖前记录原视距；之后重复 set 不会污染该值。调试覆盖是持续到显式 reset 或登出的状态，不是单 tick 效果。
- **重登录/状态替换**：登出时恢复原视距并清除雾色；重登录后不会继承上一会话的调试覆盖。若未来灾种需要持续效果，应由灾种在生效期间重复发送，不依赖重登录后的残留状态。
- **药水效果**：通过 `ServerPlayer#addEffect(MobEffectInstance)` 正常施加，尊重 duration/amplifier 单位与香草覆盖规则；已有更强同类效果时可能被拒绝，命令会报告被拒目标。
- **强制天气仅客户端显示**：`forceWeather` 只发 clientbound 载荷，改的是客户端 `Level.rainLevel`/`thunderLevel`（雷暴还要 `thunderLevel = 1`，因为香草的 `getThunderLevel` 会再乘 `getRainLevel`），`LevelRenderer` 的雨雪渲染与天空变暗读取这两个值。服务端天气循环、`ServerLevel` 等级数据、降水 tick 均不读取也不修改；不生成闪电实体，也不提供持续时间/强度/服务端天气切换。命令为 `rain`/`thunder`/`snow`/`stop`。
- **强制降水忽略群系**：香草 `LevelRenderer.renderSnowAndRain` 先用 `Biome.hasPrecipitation()` 跳过无降水群系（如沙漠），再用 `Biome.getPrecipitationAt(BlockPos)` 按温度与高度决定 `RAIN`/`SNOW`。客户端-only Mixin `LevelRendererMixin` 在该方法内重定向这两个调用：`RAIN`/`THUNDER` 返回 `Biome.Precipitation.RAIN`，`SNOW` 返回 `Biome.Precipitation.SNOW`，没有强制天气时调用原群系方法。注入只存在于客户端渲染器，不修改共享 `Biome`、气候设置、`Level` 或集成服务器，也不改服务端天气逻辑。三种类型都设 `rainLevel = 1`（`renderSnowAndRain` 以 `getRainLevel() > 0` 为门槛）；`RAIN`/`SNOW` 设 `thunderLevel = 0`，`THUNDER` 设 `thunderLevel = 1`。原版 `tickRain` 的落地水花与雨声不在本次 `renderSnowAndRain` 覆盖范围内，仍按原版群系判定。
- **每 tick 维持覆盖**：香草只在收到天气包时写这两个字段，`setRainLevel`/`setThunderLevel` 会同时写当前值与插值前值，因此客户端在 `ClientTickEvent.Post` 每 tick 重新写入强制值，避免旧的插值字段造成闪烁；期间若服务端上报新天气，先记录为原值再覆盖。
- **停止/登出语义**：收到 stop 或登出时清除 override，并把记录的服务端最近一次天气值写回；`forcedPrecipitation()` 同时返回 `null`，Mixin 随即调用原版 `Biome.hasPrecipitation()`/`getPrecipitationAt()`，雨雪渲染恢复为原版按群系表现。停止时不新增快照、不模拟天气过渡，也不读写服务端状态。切换维度时以新 `ClientLevel` 的天气重新记录原值。
- **范围边界**：本次未新增任何灾种效果、拉取式结算或自动绑定；灾种声明后来单独加入（§10.8）。§10.2 的方块判断与效果执行仍未实现（天灾刻选中后来单独接入，见 §10.7）。

## 11. 已知限制

1. **有界**：中心永远在锚点领地半径 `R_c` 内；双层只是把笼子做大，不是无界迁徙。
2. **双层接缝**：粗格边界的分片常数位移会产生密度带；未做平滑。
3. **双层查询成本（历史实测）**：当前实现按总位移扩张枚举，检测成本约为单层 18×（历史默认 k=4、N=16 时 36 µs/玩家/tick；最大 R=8 时候选检测区更大）；粗层预筛是下一步优化项。
4. **未加载不追溯**：这是取舍，不是 bug；若需要"全图灾痕"，用独立灾痕场。
5. **渲染验证**：沙箱内无法启动 Chromium（mojo 命名管道被拒）；前端用假 DOM 回放真实 app.js 验证，另有桌面 Edge 人工确认。
6. **性能数字是 Node JS 量级**：Java 模组可能更快或同量级，量级结论不变。
7. **半径量化**：阶段按真实 tick 切换，但半径只按 20 tick 运动帧变化，最多滞后 19 tick；`startTick` 不在帧边界时 `e` 可为负。这是设计行为，不做帧内插值。
