## 1. 迁移目标与边界

### 1.1 本次要达到的行为 parity

- 同一 `(seed, dimension, config, gameTime, grid/chunk)` 下，新旧版得到相同的中心位置、覆盖结果和事件时间状态。
- 保留静态锚点、有界巢域、Catmull–Rom 游走、必选双层粗位移、200 tick 运动量化及纯函数事件表。
- 保留“每维度一个场快照 + 仅已加载区块缓存 + 跨运动步懒刷新”的服务语义。
- 保留 `/disaster ison` 的查询行为。
- 完成 Forge → NeoForge 的入口、配置、事件总线和事件类型适配，不引入旧 Gradle/Forge 元数据。

### 1.2 明确不在此次“复制旧版逻辑”内

旧版自身也没有以下能力，因此不能在迁移完成声明中写成已实现：

- 任何实际天灾效果、灾种 `kind`、逐事件动态半径；
- 主文档 §8.2 的拉取式效果结算和区块效果聚合；
- 永久灾痕、未加载区块追溯；
- 完整的世界创建时配置指纹持久化；
- 区域天气、每玩家天气包及天气 mixin；
- 粗层预筛优化或双层接缝平滑。

这些若继续实施，应另立阶段，先回到主设计文档更新实现状态与决策。

### 1.3 不复制的内容

- 旧版 `build.gradle`、`settings.gradle`、`gradle.properties`、Gradle wrapper、ForgeGradle、JDK 17 路径和镜像配置；
- 旧版 `META-INF/mods.toml`、`pack.mcmeta` 的版本相关内容；
- 旧版 `build/`、`.gradle/`、`run/`、存档、日志、缓存和 IDE 文件；
- 任何会改写 1.20.1 源工程的操作。旧版只作为只读参照。

## 3. 目标结构与数据流

本次迁移保持现有三层，不引入中心实体、中心状态机或持久化中心表。

```mermaid
flowchart LR
    S[ServerLevel seed + dimension + gameTime] --> F[DisasterField 纯函数场]
    C[FieldParams 配置快照] --> F
    L[ChunkEvent.Load] --> Q[centersAffectingChunk]
    F --> Q
    Q --> K[LevelState 已加载区块缓存]
    U[ChunkEvent.Unload] --> K
    M[200 tick 运动步变化后的 status 查询] --> K
    K --> CMD[/disaster ison]
    F --> E[event 纯函数事件表]
    E --> CMD
```

### 3.1 `field/`：跨版本行为基准

- 输入只来自种子、维度哈希、参数、tick 和网格/区块坐标。
- `fineCache` / `coarseCache` 只是当前运动步的 memoization，不是中心状态，不得持久化。
- `centerPosition` 在 200 tick 步内恒定；事件表仍按实际 tick 求值，不能按运动步量化。
- `centersAffectingChunk` 使用区块中心距离和配置半径，候选范围必须按细层与粗层最大位移扩张。
- 保留现有 purpose label、常量、运算顺序和列表顺序；迁移阶段不做“等价重构”。

### 3.2 `service/`：只管理生命周期与缓存

- `LevelEvent.Load/Unload` 管理每维度 `LevelState`。
- `ChunkEvent.Load` 求值并放入缓存；`ChunkEvent.Unload` 删除。
- `status()` 对未加载区块返回 `null`，不得为了查询而加载或创建区块状态。
- 仅在已缓存区块跨运动步时懒重算；不增加全 loaded-chunks 每 tick 扫描。
- 所有玩法求值保持服务端权威；客户端不自行根据 seed 复算。

### 3.3 `command/`：观察口而非结算器

`/disaster ison` 只读取当前已加载区块的覆盖缓存，再对命中中心调用事件表。不要把伤害、天气、刷怪或方块修改塞进命令路径。

## 4. Forge → NeoForge 适配清单

| 1.20.1 Forge | 1.21.1 NeoForge | 处理 |
|---|---|---|
| `ForgeConfigSpec` | `ModConfigSpec` | 仅替换类型和 builder 包名，配置键/默认值/范围不变 |
| `FMLJavaModLoadingContext` 构造参数 | `IEventBus` + `ModContainer` 构造注入 | 使用目标现有入口，不回退旧构造器 |
| `context.getModEventBus()` | 注入的 `modEventBus` | 生命周期监听仍走 mod bus |
| `MinecraftForge.EVENT_BUS` | `NeoForge.EVENT_BUS` | 游戏事件仍走 game bus |
| `context.registerConfig(...)` | `modContainer.registerConfig(...)` | 保持 `ModConfig.Type.COMMON` |
| `net.minecraftforge.eventbus.api.*` | `net.neoforged.bus.api.*` | 适配 `IEventBus`、`SubscribeEvent` |
| `net.minecraftforge.event.*` | `net.neoforged.neoforge.event.*` | 适配命令、服务器、区块和维度事件 |
| Forge `mods.toml` | NeoForge 模板 `neoforge.mods.toml` | 保留目标模板和 `${...}` 展开 |
| ForgeGradle / Gradle 8.4 / JDK 17 | ModDevGradle / Gradle 8.8 / JDK 21 | 使用目标 wrapper 和 toolchain |

当前使用到的 Mojang 类（`ServerLevel`、`ChunkPos`、`BlockPos`、`Component`、Brigadier 等）在旧新代码中无需额外映射改写。`fastutil` 的 `Long2ObjectOpenHashMap` 也保持原用法；若编译缺依赖，应查目标运行时依赖暴露，不改写算法容器来掩盖配置问题。

## 5. 不可破坏的设计约束

迁移审查必须逐项满足主文档的确定性铁律：

1. 不引入 `Math.random`、`ThreadLocalRandom`、系统时间、对象身份哈希或加载顺序依赖。
2. 哈希继续使用种子双字、维度、格坐标、用途标签；事件时隙另混入 slot，不能复用其他用途的随机值。
3. 运行时数学只允许既定 IEEE-754 运算与 `sqrt`；不新增三角函数、`pow/exp/log/hypot/fma` 等。
4. 网格、运动步和事件时隙对负坐标/负 tick 使用数学 floor，不能用截断除法替代。
5. 时间使用 `level.getGameTime()`，禁止改用 `dayTime`。
6. 维度 id 继续通过 `dimensionHash(level.dimension().location().toString())` 混入哈希。
7. 双层默认 `layers=2`、`coarseCells=8`、`coarseKappa=0.3`；粗层归属由**细锚点静态决定**。
8. 配置快照不得在运行中被静默改写。当前实现只是 `FieldParams` 快照，尚未完成“世界创建时冻结并持久化配置指纹”，本次不伪称补齐。
9. 不保存中心位置、事件结果或“已结算”标记，不新增 `SavedData` 来模拟中心历史。
10. 不 force-load 无限中心，不追溯未加载区块，不逐方块/逐中心 tick，不做无界候选扫描。

默认配置必须与旧版一致：`centersPerKm2=1`、`kappa=0.35`、`layers=2`、`disasterDurationSeconds=60`、`disasterRadiusChunks=4`。

## 6. 分阶段实施方案

### P0：冻结基线并准备差分样例

1. 旧版目录保持只读，记录源/目标版本和上述 11 文件清单。
2. 从旧版代码的临时副本或独立 fixture 运行器生成黄金样例；不向旧版工程写入迁移代码。
3. 将确认后的 fixture 放到目标 `src/test/resources/`，记录输入参数和算法 fixture 格式版本。
4. 位置 `x/z` 建议以 `Double.doubleToRawLongBits` 的十六进制保存，避免十进制序列化掩盖末位差异。

**产物：**可重复执行的新旧版输入/期望输出样例。

### P1：锁定纯算法 parity（源码已存在，重点为验收）

1. 不再整目录覆盖 `field/`，避免把换行符差异或后续目标端修改变成无意义 diff。
2. 逐文件核对 7 个纯场类，尤其是 purpose label、常量、运算顺序、静态粗格归属和事件互斥规则。
3. 在 `src/test/java/com/fst/naturaldisaster/field/` 添加不启动 Minecraft 的纯场测试。
4. 若采用 JUnit 5，在目标 `build.gradle` 只增加 test 依赖与 `useJUnitPlatform()`；不得借此改主运行配置。

**通过条件：**黄金样例逐位一致，边界与不变量测试全部通过。

### P2：核验 NeoForge 集成（源码已存在，重点为生命周期）

1. 按 §4 复核 4 个集成类，不重新回拷 Forge import。
2. 确认入口只注册一次 `DisasterService.INSTANCE`，命令仍由 `RegisterCommandsEvent` 注册。
3. 确认 COMMON 配置在构造入口注册，六项日志可读取。
4. 确认维度 unload 后缓存移除，区块 unload 后条目标识删除，未加载查询不触发场求值。
5. 确认 `neoforge.mods.toml`、mod id 和 `gradle.properties` 一致。

**通过条件：**静态审查无旧 Forge 引用，目标编译通过，事件 wiring 可由运行时日志和行为证明。

### P3：构建与自动验收

依次执行：

```bat
gradlew.bat compileJava
gradlew.bat test
gradlew.bat build
```

- `compileJava` 验证 NeoForge API 与 JDK 21 编译。
- 只有新增测试真实被发现并执行后，`test` 才算验收证据；当前空测试任务不代表行为通过。
- `build` 验证元数据展开与 jar 组装。
- 若失败，先区分目标 API/工具链问题与算法差异；不得通过修改黄金样例来迎合错误结果。

### P4：专用服务器冒烟

1. 执行 `gradlew.bat runServer`，确认 common setup 的六项配置日志和 `Natural Disaster attached to server instance`。
2. 检查 `run/logs/latest.log`，无 mod loading、config、事件注册或类加载异常。
3. 在玩家所在已加载区块执行 `/disaster ison`，分别观察无覆盖、覆盖但空闲、活动事件三种输出（可通过等待/选择位置实现）。
4. 用控制台/RCON 对未加载区块执行查询，应得到“不参与天灾”提示；force-load 仅作为**测试夹具**验证可查询，移除后确认卸载恢复提示，不能把 force-load 变成产品机制。
5. 在至少两个维度检查维度隔离与卸载/重进无异常；重启服务器确认没有线程、缓存或反序列化相关异常。

### P5：文档收尾

- 把实际执行的命令、测试结果、运行时结果和发现的问题回填到主设计文档 §10.4。
- 只有全部 parity 与运行验收通过后，才把迁移标为完成。
- 若之后开始天灾效果或天气，另建实施文档，不把新能力混入本次旧版 parity 结论。

## 7. 测试矩阵与验收口径

### 7.1 跨版本黄金样例

至少覆盖以下类别，并对旧版与新版使用完全相同的 `FieldParams`：

| 类别 | 建议输入 |
|---|---|
| 种子/维度 | `0`、`-1`、`Long.MIN_VALUE`、非零常规种子；overworld、nether、自定义维度字符串 |
| tick | `-401`、`-200`、`-1`、`0`、`1`、`199`、`200`、`201`、事件边界及较大 tick |
| 网格/区块 | 原点、负坐标、正负边界、`±3e7` 方块附近对应网格/区块 |
| 参数 | 默认双层；`N=16`；显式 `layers=1` 对照；不同 duration/radius |
| 输出 | `dimensionHash`、`motionStep`、`centerPosition`、`centersAffectingChunk`、`event` |

断言要求：

- 位置使用原始 double bit 精确比较，而非宽松 epsilon。
- `CenterHit` 的数量、顺序、网格 id、位置和半径完全一致。
- 事件的 `active/startTick/elapsed/remaining` 完全一致。
- 同一输入重复查询、改变查询顺序后结果一致；缓存只能影响性能，不能影响结果。

### 7.2 算法不变量

- 同一运动步内位置恒定，跨步按纯函数重算；负 tick 的 step 使用 floor。
- 双层保持静态粗格归属，不能因当前位置跨粗格而换粗层中心。
- 每次活动事件恰好持续配置 duration，之后至少一个完整空时隙；occupancy 解释仍为 `p(1-p)`，不是 `p`。
- 覆盖查询与按充分扩张候选格的暴力枚举一致，且不漏加载区外中心对区块的覆盖。
- 不出现主文档禁止的随机源、运行时三角函数、持久中心状态和无界扫描。

### 7.3 服务与性能验收

- 已加载区块求值、卸载删除、跨 200 tick 懒刷新行为与旧版一致。
- 未加载区块 `status()` 为 `null`，且不新建缓存项。
- 多玩家/多维度不共享错误的维度场或区块状态。
- 迁移阶段不以旧新 JVM/MC 的墙钟时间严格相等作为门槛；先保证候选范围有界、无每 tick 全缓存扫描、无逐方块效果。性能测量结果单独记录，双层预筛优化另立任务。

### 7.4 完成定义（DoD）

必须同时满足：

- [ ] 7 个纯场文件通过跨版本黄金样例和不变量测试。
- [ ] 4 个集成类无遗留 Forge API，配置及注册行为通过运行时检查。
- [ ] `compileJava`、真实测试任务和 `build` 成功。
- [ ] 专用服务器日志、命令、加载/卸载、维度与重启冒烟通过。
- [ ] 主设计文档的实现状态按实际结果更新，未实现能力仍明确标为未实现。

| 风险 | 处理 |
|---|---|
| 再次整目录复制，覆盖目标端 NeoForge 适配或新修改 | 以当前文件为基线逐文件审查；纯算法只在有证据时修改 |

## 9. 推荐执行顺序

1. 先建立旧版黄金 fixture 与目标纯场测试。
2. 对当前已存在的 11 文件做最小修正；原则上纯算法零改动，集成类只保留 NeoForge 适配。
3. 编译与测试通过后，再做服务器运行时验收。
4. 最后同步主设计文档状态。
5. 后续才进入事件 `kind`、实际效果、拉取式结算或区域天气。

这一路径既保留 1.20.1 的可验证行为，也遵守天灾系统“纯函数、局部有界查询、只处理已加载区域、不保存中心历史”的整体设计。
