# 区域天气系统：设计与决策（v0.1）

> 版本：v0.1 · 2026-10-21
> 状态：**设计稿，尚未实现**。
> 本文只负责“区域天气”子系统：虚拟天气场、客户端视觉、服务端玩法注入、边界与验收。
> 天灾中心、事件表、拉取式结算仍以《天灾中心系统-设计与决策汇总.md》为准；两者冲突时，中心场/事件表以主文档为准，天气子系统以本文为准。
> 工程基线：Minecraft 1.21.1 / NeoForge 21.1.219 / Mojang mappings。
> 原版天气事实核对基线仍为 1.20.1（见 §2），迁到 1.21.1 后需重新复核。

---

## 0. 一句话

服务端维护一套**纯函数的虚拟天气场**，按玩家/区块求值；客户端不写渲染代码，只接收**每玩家原版天气包**；服务端在 3 个调用点注入，复用或抑制原版天气效果。视觉层几乎零侵入，玩法层有最低侵入下限。

## 1. 决策摘要

| # | 决策 | 状态 |
|---|---|---|
| W1 | 虚拟天气是纯函数，不做持久状态；不保存到 level.dat | 已决策 |
| W2 | 客户端视觉走原版 `ClientboundGameEventPacket`，每玩家独立发送 | 已决策 |
| W3 | 服务端全局天气基态固定为**晴**，原版全局天气不参与玩法 | 已决策 |

| W8 | 无位置 API 的消费者（Bee、怪物生成光照、WeatherCheck 等）v1 接受全局晴天 | 已决策 |

## 2. 原版天气事实（1.20.1）

### 2.1 一份状态，所有维度共享读

- 主世界 `PrimaryLevelData` 持有唯一一份 `raining` / `thundering` / `rainTime` / `thunderTime` / `clearWeatherTime`，写进 `level.dat`。
- 其他维度由 `DerivedLevelData` 包装主世界数据：所有天气 getter 转发，**所有天气 setter 都是空实现**。
- `ServerLevel#advanceWeatherCycle` 每个维度都会执行，但只有 `dimensionType().hasSkyLight()` 的维度会推进本地 `rainLevel` / `thunderLevel`。原版只有主世界满足；下界、末地 `has_skylight=false`，不会每 tick 推进天气。
- 注意：`ServerLevel` 构造时会调用 `Level#prepareWeather()`，它按全局 `levelData.isRaining()` 直接初始化本地 `rainLevel` / `thunderLevel`。所以无天空维度在加载瞬间理论上可能继承一个非零值；本方案在服务端启动、`LevelEvent.Load` 和每 tick 的 `LevelTickEvent.Pre` 显式清零，不依赖“无天空维度一定为 0”的假设。
- 结论：表现上是“主世界一份天气，所有有天空的维度共享；无天空维度正常不推进天气”。

### 2.2 推进与广播

- `advanceWeatherCycle` 每 tick 修改全局 `levelData` 的 rain/thunder 计时器，并以 `0.01/tick` 逼近目标 `rainLevel` / `thunderLevel`。
- 向该维度所有玩家广播 `START_RAINING` / `STOP_RAINING` / `RAIN_LEVEL_CHANGE` / `THUNDER_LEVEL_CHANGE`。
- 玩家加入时，`PlayerList#sendLevelInfo` 只在 `isRaining()` 为真时补发初始天气包。

### 2.3 判定链

```text
Level.isRaining()       = rainLevel > 0.2
Level.isThundering()    = thunderLevel * rainLevel > 0.9，且维度有天空、无天花板
Level.isRainingAt(pos)  = isRaining()
                          && canSeeSky(pos)
                          && 高度图不高于 pos
                          && Biome.getPrecipitationAt(pos) == RAIN
```

注意：`isRainingAt` 只认 `RAIN`，不认 `SNOW`。雪区不会触发淋湿、耕地补水、火焰熄灭这些“下雨”逻辑。

### 2.4 区块级效果

`ServerLevel#tickChunk` 中：

- `flag = isRaining()`；
- 自然雷击：`flag && isThundering() && isRainingAt(target)`；
- 积雪、炼药锅、`handlePrecipitation`：只在 `flag` 为真时；
- 结冰：只看群系温度，与 `flag` 无关。

### 2.5 客户端渲染

- `ClientPacketListener` 收到 `RAIN_LEVEL_CHANGE` / `THUNDER_LEVEL_CHANGE` 后只改 `ClientLevel.rainLevel` / `thunderLevel`；`START_RAINING` / `STOP_RAINING` 额外改 `levelData.raining`。
- `LevelRenderer#renderSnowAndRain`、`LevelRenderer#tickRain`、`FogRenderer`、`ClientLevel#getSkyDarken` 全部读这一个标量。
- 雨还是雪由 `Biome.getPrecipitationAt` 按群系温度决定；`hasPrecipitation=false` 的群系（沙漠、恶地）不画雨。
- `Level#setRainLevel` 会把 `oRainLevel` 和 `rainLevel` 同时设为同一个值，**不做插值**。

### 2.6 对设计的直接约束

1. 客户端只有一个 `rainLevel`，所以“每玩家天气”容易，“视野内逐列分区”必须改客户端渲染。
2. 客户端拿到的是混淆后的 seed，不能自己复算中心场；天气值应由服务器下发。
3. 原版没有天气事件；要复用或抑制原版效果，只能在调用点注入。
4. `isRaining()` / `isThundering()` 没有位置参数，无法用一个钩子局部化。

## 3. 虚拟天气模型

### 3.1 天气源接口

```java
public interface WeatherSource {
    /** 纯函数：给定维度、区块、gameTime，返回该区块的天气。 */
    WeatherSample sample(ServerLevel level, ChunkPos chunk, long gameTime);
}

public record WeatherSample(float intensity, boolean thundering) {
    // intensity ∈ [0, 1]；服务端判定降水用 intensity > 0.2，与 Level#isRaining 一致
}
```

- `intensity` 是客户端雨量；`thundering` 是雷暴标记。
- 服务端“是否降水”统一用 `intensity > 0.2`，不要引入第二套阈值。
- 多个事件重叠时：`intensity = max(...)`，`thundering = any(...)`。
- v1 的天气源建议直接由主文档的事件表派生：事件 `kind` 属于降水/雷暴类时，按事件圆与区块中心判定。天气半径复用事件半径，不新增无界扫描。

### 3.2 纯函数与配置指纹

- 输入必须包含：世界种子、维度、区块坐标、`gameTime`、用途标签。
- 禁止 `Math.random`、`System.currentTimeMillis`、对象身份哈希、加载顺序。
- 新增天气参数（事件到天气的映射、强度、雷暴标记、区块取整规则、阈值、缓存版本）必须进入**配置指纹**；改任何一项都可能改变已有世界的天气。
- 不保存天气状态；读档后按 `(seed, config, gameTime, dimension, chunk)` 重算。
- 客户端不需要种子；服务器只发当前值。

### 3.3 区块取整与缓存

- 天气存在性按**区块**取整，与主文档 §8.4 一致；`isRainingAt` 只在该区块天气为降水时，继续执行原版天空/高度/群系检查。
- 每 tick 维护一个瞬态 `WeatherCache`：key = `(dimension, chunkX, chunkZ)`，value = `WeatherSample`；tick 边界清空，miss 时调用纯函数。
- `WeatherCache` 提供 `hasPrecipitationNear(level, chunk, radius)`：按需采样邻居区块并复用缓存，供 `FireBlock` 的跨区块边界检查使用。
- 缓存只是 memoization，不改变结果；没有持久化。
- **性能红线**：不要在每个区块的 `tickChunk` 里重新跑一次 `centersInRect`。每 tick 先按玩家/加载区拉取一次附近事件，得到当 tick 的活动事件列表；`sample(chunk)` 只对这个小列表做距离测试。缓存 miss 且不在预计算区域时，再做一次有界纯查询。
- 天气半径/事件半径参与查询扩张，查询半径必须有上界，沿用主文档的事件半径上限。

## 4. 视觉层：每玩家原版天气包

### 4.1 协议

服务端按玩家当前区块求值，直接发送原版包：

```java
ServerLevel level = player.serverLevel();
WeatherSample w = weatherCache.sample(level,
        new ChunkPos(player.blockPosition()), level.getGameTime());

// 无降水群系不发送非零雨量，避免“有雾/天空变暗但没有雨粒子”
if (!level.getBiome(player.blockPosition()).value().hasPrecipitation()) {
    w = new WeatherSample(0.0F, false);
}

player.connection.send(new ClientboundGameEventPacket(
        ClientboundGameEventPacket.RAIN_LEVEL_CHANGE, w.intensity()));
player.connection.send(new ClientboundGameEventPacket(
        ClientboundGameEventPacket.THUNDER_LEVEL_CHANGE,
        w.thundering() ? w.intensity() : 0.0F));
```

- 先发 rain，再发 thunder；`ClientLevel#getThunderLevel` 会乘以 rain level。
- 雷暴事件建议 `intensity = 1.0`。客户端 `getThunderLevel = thunderLevel * rainLevel`，只有接近 1 才会被判定为雷暴并出现闪白；`intensity=0.5 + thundering=true` 在客户端通常看不到雷暴效果。
- v1 **不依赖** `START_RAINING` / `STOP_RAINING` 驱动渲染；`RAIN_LEVEL_CHANGE` 就足够驱动雨雪几何、雾、天空变暗和雨声。
- 如果后续需要客户端 `levelData.raining` 一致，可以补发 `START_RAINING` / `STOP_RAINING`；注意 `STOP_RAINING` 会把 `rainLevel` 置 1，必须紧接着补发实际值。

### 4.2 发送时机

- 玩家登录完成后、首次 tick。
- 玩家重生、换维度、传送后。
- 玩家所在区块的天气值变化时。
- 数值变化超过阈值（建议 `0.01`）时；静止时不发包。

### 4.3 过渡

- 服务端可以用 `0.01/tick` 步进模拟原版过渡，最多约 100 tick；也可以直接 snap。
- 推荐：跨区域时快速过渡（10–20 tick），避免天气突变；进入/离开降水状态时再按原版速度补齐。
- 过渡期间每 tick 每玩家 1 个包，20 包/秒，相对区块包可忽略。

### 4.4 限制

- 一个客户端只有一个 `rainLevel`，所以是“**每玩家一个天气**”，不是“视野内左右分区”。
- 玩家站在边界上会整屏切换；无法在同一屏内同时看到雨区和晴区。
- 沙漠/恶地不画雨粒子；暖群系不会下雪。v1 尊重原版群系降水规则。
- 玩家在无降水群系时，服务端应发送 `intensity = 0`，避免出现“有雾、有天空变暗、但没有雨粒子”的违和画面。
- 第三人称/旁观者相机离开玩家所在区块时，视觉天气仍按玩家区块，存在轻微不一致；v1 接受。

## 5. 玩法层：服务端注入

### 5.1 全局基态固定为晴

- 服务端启动后把 `doWeatherCycle` 设为 `false`，并对所有已加载 `ServerLevel` 清零；`LevelEvent.Load` 负责覆盖之后才加载的维度。之后每个 `LevelTickEvent.Pre` 再次将全局天气重置为晴：
  - `setWeatherParameters(0, 0, false, false)`；
  - `setRainLevel(0)`、`setThunderLevel(0)`。
- 这些处理器必须加 `level instanceof ServerLevel`（或 `!level.isClientSide`）守卫。`LevelTickEvent` / `LevelEvent.Load` 在客户端也会触发；客户端清零会直接覆盖天气包驱动的 `rainLevel`，导致永远不下雨。
- `LevelEvent.Load` 的清零不能省：`ServerLevel` 构造时 `prepareWeather()` 可能从全局 `isRaining()` 继承一个非零 `rainLevel`，而 `advanceWeatherCycle` 对无天空维度不会自动把它降下来。
- 目的：`Level#isRaining()` / `isThundering()` 在原版所有无位置消费者眼里始终为 false，不会产生全局误判。
- `/weather` 仍能改全局字段，但下一个 tick 会被重置；如果希望 `/weather` 成为调试入口，单独拦截命令，不要依赖全局字段。
- 不要在新增代码里用 `level.isRaining()` 判断虚拟天气；统一走 `WeatherSource` / `WeatherCache`。

### 5.2 注入点

| # | 目标 | 注入方式 | 作用 |
|---|---|---|---|
| S1 | `Level#isRainingAt(BlockPos)` | 重定向方法内部对 `isRaining()` 的调用 | 让原版天空/高度/群系检查继续执行，只替换“全局是否下雨”这一项 |
| S2 | `ServerLevel#tickChunk` | 重定向 `isRaining()`、`isThundering()` 两处调用 | 控制积雪、炼药锅、降水、自然雷击 |
| S3 | `FireBlock#tick` | 重定向两处 `isRaining()` 调用 | 全局晴时，虚拟雨仍能熄火/抑制蔓延 |

#### S1：`Level#isRainingAt`

不要用 HEAD 重写整个方法；用 `@Redirect` 替换方法内部的 `isRaining()` 调用：

```text
ServerLevel: return weatherCache.sample(this, new ChunkPos(pos), gameTime).intensity() > 0.2
ClientLevel: return 原版 isRaining()
```

这样原版的 `canSeeSky`、高度图、`Biome.getPrecipitationAt == RAIN` 全部保留，语义最接近原版：

- 干区块返回 false；
- 湿区块且露天、群系降水为 RAIN 才返回 true；
- 雪区仍然返回 false（`Precipitation.SNOW` 不等于 RAIN），与主文档的“瞬时效果”语义一致。

`Level#isRainingAt` 是 common 代码，注入时必须加 `!isClientSide` 守卫，客户端继续使用包驱动的 `rainLevel`。

#### S2：`ServerLevel#tickChunk`

- 把 `boolean flag = this.isRaining()` 中的 `isRaining()` 重定向为：`weatherCache.sample(this, chunk.getPos(), gameTime).intensity() > 0.2`。
- 把雷击条件中的 `isThundering()` 重定向为：`weatherCache.sample(this, chunk.getPos(), gameTime).thundering()`。
- 雷击目标仍由 `isRainingAt(target)` 判定，S1 已处理。
- 结冰保持原版：只由群系温度决定，不因虚拟天气关闭。
- 一个区块内如果跨天气边界，按区块中心/区块缓存取整；这是主文档 §8.4 的既定取舍。

#### S3：`FireBlock#tick`

`FireBlock#tick` 除了 `isNearRain` 还**单独**检查 `isRaining()`；全局晴时，仅靠 S1 不会熄火。重定向该方法的两个 `isRaining()` 调用：

```text
// hasPrecipitationNear 检查以 firePos 所在区块为中心的 3×3 区块
return weatherCache.hasPrecipitationNear(level, new ChunkPos(firePos), 1)
```

这里用**区域级“是否降水”**，不要用 `isRainingAt(firePos)` 替代外层条件。原版语义是“区域在下雨 + 附近有露天雨点”，火焰在屋檐下但旁边露天时仍可能被浇灭；用区域级条件可以保留这个行为。`isNearRain` 继续走 S1，负责露天判定。

边界处理：外层不要只看火焰所在的一个区块，应取火焰区块及其 8 邻域（或火焰位置与四邻）的虚拟降水。只查单区块的话，湿区隔壁的干区火焰不会熄火；跨区块边界会漏判。火焰随机 tick 很稀疏，3×3 缓存查找的成本可以忽略。

#### 无位置消费者

以下代码直接调用 `isRaining()` / `isThundering()`，没有位置参数，v1 接受其在全局晴天下始终为 false：

- `Bee`、`BeehiveBlockEntity`（蜜蜂归巢/出巢）；
- `Monster`（雷暴时的刷怪光照）；
- `Fox`、`Panda`（雷暴行为）；
- `WeatherCheck` 掉落谓词；
- `LightningRodBlock` 的雷暴粒子；
- `ThrownTrident` 的引雷；
- `Level#updateSkyBrightness`（服务端天空变暗/刷怪光照）。

如果产品要求这些也随区域变化，需要逐个注入；这会把“3 个注入点”扩大为一组消费者补丁。v1 不做。

## 6. 可选：逐列渲染

只有以下需求才需要客户端渲染层：

- 同一屏内左边下雨、右边晴；
- 沙漠中下雨；
- 暖群系下雪；
- 天气边界需要平滑过渡，而不是整屏切换。

可选路径：

1. **非 mixin**：监听 `RegisterDimensionSpecialEffectsEvent`，注册自定义 `DimensionSpecialEffects`，覆写 `renderSnowAndRain` / `tickRain` 返回 `true`，自己绘制。
   - Forge 的 `IForgeDimensionSpecialEffects` 提供了这两个钩子。
   - 需要额外的天气同步包，把玩家附近的区块天气快照发给客户端；不能依赖客户端自己算（客户端只有混淆 seed）。
2. **mixin**：直接改 `LevelRenderer#renderSnowAndRain` / `tickRain`，按列查询虚拟天气。
   - 方法私有，跨版本稳定性差；不推荐作为 v1。

注意：即使逐列渲染，`FogRenderer` 和 `ClientLevel#getSkyDarken` 仍读 `Level#getRainLevel`。要局部化雾/天空，仍需要每玩家包提供本地标量，或额外注入。

v1 明确不做逐列渲染；先验证每玩家包的视觉效果是否足够。

## 7. 生命周期与边界

### 7.1 `/weather`、睡觉、doWeatherCycle

- `doWeatherCycle=false` 防止原版随机改天气；不阻止 `/weather`。
- `doWeatherCycle` 是可见的世界设置并写入 `level.dat`。管理员改回 `true` 时，`LevelTickEvent.Pre` 的清零仍能兜底，但同一 tick 内原版仍可能短暂下雨，因此不要依赖运行期改回。
- 每个 `LevelTickEvent.Pre` 重置全局晴，保证 `/weather` 最多影响一个 tick。
- 睡觉不会触发 `resetWeatherCycle`，因为全局 `isRaining()` 为 false。
- 如果以后把 `/weather` 作为调试入口，拦截命令并写入一个**非持久**的 `WeatherOverride`；不要写全局 `levelData`。

### 7.2 登录、重生、换维度

- 登录完成后首 tick 发一次当前天气。
- `PlayerEvent.PlayerRespawnEvent`、`PlayerEvent.PlayerChangedDimensionEvent` 后重新发。
- 换维度后客户端是新的 `ClientLevel`，天气字段归零，必须重发。
- 服务端只给玩家所在维度发；Nether/End 不发。

### 7.3 多人、多维度

- 每个玩家独立求值；同一区块的玩家共享同一个 `WeatherSample`。
- 玩家分散时，成本按“互不相邻的加载区域数”增长，不按玩家数增长。
- 维度混入哈希；天气源必须使用 `level.dimension()`。
- v1 只在 `hasSkyLight() && !hasCeiling()` 的维度启用虚拟天气，和原版“能下雨的维度”一致；Nether/End 始终晴。

### 7.4 与其他 mod

- 其他天气 mod 可能改全局天气、发天气包或注入同一方法；本方案固定全局晴会与其冲突。
- 若同时存在，需要明确加载顺序/兼容策略；v1 不做兼容层。
- 注入点尽量窄：只重定向需要的调用，不覆盖整个方法，减少与其他 mixin 的冲突。

## 8. 性能

- 每玩家每 tick 一次天气查询：O(1) 缓存读取 + 变化时发包。
- 每 tick 活动事件列表按加载区拉取一次；`sample(chunk)` 只做小列表距离测试，不重复 `centersInRect`。
- 缓存按 tick 清空；无持久化、无跨 tick 失效问题。
- 服务端注入点只增加一次哈希/缓存查找，成本远低于区块 tick 本身。
- 禁止逐方块扫描、逐方块天气计算、逐中心遍历。
- 验收目标：天气缓存构建 + 注入点开销 `< 0.1 ms/玩家区域/tick`（量级目标，实测后回填）。

## 9. 验收

### 9.1 确定性

- 同一 `(seed, config, gameTime, dimension, chunk)` 重复求值结果一致；
- 负坐标、负 tick、大坐标（±3e7）正确；
- 读档/重启后同一 tick 结果一致；
- 改变天气参数会改变配置指纹。

### 9.2 服务端

- 全局 `level.isRaining()` / `isThundering()` 始终为 false（除非调试覆盖）。
- 干区块：`isRainingAt` 为 false；火焰不熄；炼药锅不填；不积雪；无自然雷击。
- 湿区块：露天且群系降水为 RAIN 时 `isRainingAt` 为 true；火焰可熄；炼药锅可填；冷群系积雪。
- 雷暴区块：自然雷击只在该区块发生；`isThundering` 注入生效。
- 结冰不受虚拟天气影响。
- `/weather rain` 下一 tick 被重置，无持续全局效果。
- Nether/End 不发天气包、不产生虚拟天气。
- 雪区：`isRainingAt` 仍为 false（只认 RAIN）；积雪由 `tickChunk` 的虚拟降水标志驱动。

### 9.3 客户端

- 两个玩家在不同区域，看到不同雨量/雷暴。
- 玩家跨区域后，客户端在一个 tick 内收到新值。
- 登录、重生、换维度后不残留上一维度天气。
- 沙漠/恶地不出现雨粒子；无降水群系不发非零 intensity。
- 雨声、雾、天空变暗与雨量一致。
- 已知限制：同屏不能分区；边界整屏切换。

### 9.4 性能

- 20 玩家、441 加载区块场景下，天气系统不产生可感知 tick 峰值；
- 不出现逐方块/逐中心扫描；
- 缓存命中率、每 tick 查询次数可观测（调试计数）。

## 11. 被否方案

| 方案 | 否掉原因 |
|---|---|
| 只发每玩家天气包，不改服务端 | 视觉可行，但原版火焰/炼药锅/积雪/雷击仍按全局天气，无法满足“局部天气真正生效” |
| 全局基态设为“任意区域有雨就下雨” | 火焰湿区自动生效，但 Bee、怪物生成光照、WeatherCheck、服务端天空变暗会全局误判 |
| 改 `Level#isRaining()` 为虚拟值 | 没有位置参数，所有消费者拿到同一个值；等于把局部天气又变成全局 |
| 完全自实现天气效果，零 mixin | 火焰随机 tick 没有 Forge 事件；扫描/跟踪火焰成本高于一个 redirect |
| 客户端按 seed 自己复算天气 | 客户端只有混淆 seed，且需要同步配置指纹；协议和版本负担更大 |
| v1 做逐列渲染 | 需要自定义渲染 + 区域天气同步；先把每玩家包跑通 |
| 逐方块天气判定 | 违反主文档性能红线；区块取整已经足够 |
